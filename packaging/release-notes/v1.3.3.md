## DANFE Renamer 1.3.3

Esta versão conserta o **Mostrar na pasta**, que abria a pasta errada, faz a tela
**Detalhes** mostrar só o que interessa e **não deixa mais o PDF se perder**
quando um XML não pode ser renomeado.

### O que mudou
- **"Mostrar na pasta" abre a pasta certa.** Quando o caminho do arquivo tinha um
  espaço — `C:\...\Notas fiscais\...`, por exemplo —, o Windows abria a pasta
  **Documentos** em vez da pasta do arquivo. O Explorer não lê a linha de comando
  como os outros programas: ele não aceita o comando e o caminho dentro das mesmas
  aspas, e era isso que o programa fazia. Agora só o caminho vai entre aspas, e a
  pasta do arquivo abre com ele já selecionado.
- **Um XML que não pôde ser renomeado não perde mais o PDF.** Antes, quando um
  arquivo falhava, o DANFE era gerado numa pasta temporária e apagado junto com
  ela — ou nem chegava a ser gerado. Agora o PDF é gerado de qualquer forma e fica
  na subpasta **`_unrenamed`** do lote, com o nome do XML de origem
  (`nota-sem-destinatario.xml` → `_unrenamed\nota-sem-destinatario.pdf`).
- **A linha do arquivo que falhou aponta para esse PDF**, então **Abrir PDF (sem
  nome)** na tela Detalhes abre o documento e **Mostrar na pasta** leva até ele —
  é só renomear à mão. O botão muda de nome conforme o que ele abre: numa linha
  renomeada ele continua **Abrir cópia renomeada**.
- **Os relatórios dizem onde o arquivo ficou.** A nova coluna `output_file`
  ("Arquivo de saída" no HTML) traz o caminho dentro da pasta do lote, tenha o
  arquivo o nome combinado ou não. Assim a pasta nunca tem um PDF que nenhuma
  linha explica.
- **A tela Detalhes ganhou um filtro: Mostrar → Todos os arquivos / Somente falhas
  / Somente sucessos.** Num lote grande, quem só quer resolver o que deu errado
  não precisa passar os olhos por tudo o que já foi renomeado.
- **Um XML salvo em outra codificação não falha mais.** Se o programa que gerou o
  XML gravou o arquivo em ISO-8859-1 (Latin-1) — comum em sistemas mais antigos —, o
  PDF não era gerado e o motivo dizia **Não foi possível gerar o PDF a partir do
  XML**, mesmo com todos os dados certos no arquivo. Agora o conversor lê o XML na
  codificação que o próprio arquivo declara, como o leitor de dados já fazia.
- **A data de emissão sai sempre no mesmo formato.** Nos relatórios e na tela,
  um arquivo vindo de PDF mostrava `16/09/2026` e o mesmo arquivo vindo do XML
  mostrava `16.09.2026`. Agora é `16.09.2026` nos dois casos, como no nome do
  arquivo.
- **O motivo específico de cada falha agora também é traduzido** — e o mesmo vale
  para as observações. Antes, esse detalhe (a linha **Causa**, a coluna *Motivo*,
  a última linha do `--verbose`, a coluna `reason` dos relatórios) vinha escrito em
  inglês, montado pelas partes internas do programa — por exemplo `Could not open
  PDF: …` ou `emission date printed differently in the document: …`. Agora cada
  parte registra um código e os valores da frase, e a frase é montada no idioma
  escolhido: **Não foi possível abrir o PDF: …**, **A data de emissão aparece de
  mais de uma forma: …**. O que a biblioteca ou o Windows respondeu continua lá,
  dentro da frase e exatamente como veio, porque isso é evidência e não se traduz.
- **O relatório ganhou a coluna `detail_code`**: o código estável do detalhe
  (`PDF_OPEN_FAILED`, `COPY_FAILED`…), para um script não precisar ler frase
  nenhuma. As colunas `status`, `failure_code` e `detail_code` são iguais em
  qualquer idioma.
- **"Somente falhas" inclui os arquivos ignorados e os com erro** — os dois são
  arquivos que precisam da sua atenção, e é por isso que o resumo conta os dois.
- **A lista sempre diz quanto do lote está mostrando**: `1 de 33 arquivos`. Sem
  essa linha, um filtro ligado parecia um lote que tinha perdido arquivos.
- O filtro vale para o lote que está na tela: ele continua ligado se você trocar
  o idioma, e o próximo lote abre mostrando todos os arquivos de novo.

### Outras correções
- **Um nome que não dá para montar agora é um erro, não um nome torto.** Quando o
  nome da empresa no documento só tem caracteres que o Windows não aceita em nome
  de arquivo (por exemplo `///`), o arquivo era renomeado com o espaço do nome
  vazio — `16.09.2026_NF 1234 -  - 1.234,56.pdf`. Agora isso é reportado como
  falha, e o PDF fica em `_unrenamed` para ser renomeado à mão.
- **Passar de novo na mesma pasta não reprocessa as cópias.** A subpasta
  `DANFE_Renamed`, onde os lotes são gravados, não é lida como entrada: antes,
  numa terceira passada pela mesma pasta, os PDFs dos lotes anteriores entravam no
  lote novo como se fossem notas.
- **A linha de comando fala a língua dos relatórios.** O resumo, as contagens, os
  motivos e as mensagens saem no idioma escolhido (`--language` vale para o
  console também), as contagens são as mesmas que a janela e os relatórios
  mostram, e uma simulação (`--dry-run`) começa dizendo que nada foi gravado.
- **O relatório em português não repete o motivo em inglês.** A coluna *Motivo* do
  HTML mostrava a frase em português e, logo depois, a mesma frase do catálogo em
  inglês. Agora ela aparece uma vez, no idioma do relatório.

### Como usar
1. Baixe `DANFE_Renamer_v1.3.3.exe` abaixo (seção **Assets**).
2. Dê dois cliques. Se o Windows mostrar **"O Windows protegeu o seu PC"**,
   clique em **Mais informações** e depois em **Executar assim mesmo** (é normal
   para programas sem assinatura digital).
3. Processe o lote normalmente.
4. Clique em **Ver detalhes**. Use **Mostrar: Somente falhas** para ver só o que
   não foi renomeado; selecione um arquivo e clique em **Mostrar na pasta** para
   abrir a pasta onde ele está, ou em **Abrir PDF (sem nome)** para abrir o DANFE
   que ficou guardado em `_unrenamed`.

### Detalhes técnicos
- Windows 10/11 (64 bits). Não precisa instalar Python nem nada.
- Sem rede, sem telemetria: nada é enviado para lugar nenhum.
- As regras de segurança continuam iguais: os arquivos originais nunca são
  modificados, nada é sobrescrito e um arquivo duvidoso é ignorado com o motivo
  escrito. O PDF guardado em `_unrenamed` é uma cópia a mais dentro do lote, nunca
  no lugar do arquivo original.
- Por dentro: as três definições repetidas de `MAX_VALUE_DISTANCE` viraram uma, as
  duas traduções que ninguém usava saíram, a função `analyze_source` que ninguém
  chamava saiu, e `run_batch` agora recusa copiar sem uma pasta de saída em vez de
  gravar um lote na pasta onde o processo estiver aberto.

### English summary
**Show in folder** opened the wrong folder. Windows Explorer does not read its
command line as an argument list, and the application handed it the `/select,`
switch and the path quoted as a single word, which Explorer answers by opening
its default folder - Documentos. Only a path containing a space showed it, so a
batch read from a folder like `Notas fiscais` went to Documentos while a batch
read from `C:\notas` looked fine. The quotes now wrap the path alone and the path
is made absolute for Explorer.

**An XML the batch could not name no longer loses its PDF.** The DANFE used to be
rendered into a staging folder and deleted with it - or never rendered at all -
leaving somebody who has to finish the file by hand with nothing to finish. It is
now generated anyway and kept in the batch's `_unrenamed` folder under the name
of the XML it came from; the row that reports the failure points at it, **Open PDF
(not renamed)** opens it, and the reports name it in a new `output_file` column
("Output file"), so no file sits in the batch folder that no line explains. The
button still says **Open renamed copy** for a row that has one. Nothing is kept
where there is no DANFE to keep: an XML that could not be read or is not an
NF-e/NFC-e has none, and a PDF input is the reader's own file, which the batch
never moved.

**An XML saved in another encoding no longer fails.** When the program that
wrote the XML saved it as ISO-8859-1 (Latin-1) - common in older systems - the PDF
was not generated and the reason read *PDF could not be generated from the XML*,
however right the data was. The converter now reads the file in the encoding the
XML itself declares, which is what the field reader already did. The emission date
also reads the same way whichever file it came from (`16.09.2026`, as in the file
name, instead of `16/09/2026` from a PDF and `16.09.2026` from an XML).

**The detail behind a failure is translated too.** The specific reason - the
*Cause* line, the report's *Reason* column, the last line of `--verbose` - used to
be English prose written by the application's own layers (`Could not open PDF: …`,
`emission date printed differently in the document: …`). A layer now records a
stable code and the values a sentence needs, and the sentence is built in the
chosen language - **Could not open the PDF: …**, **Não foi possível abrir o PDF:
…** - with what the library or Windows answered kept inside it, unchanged: that is
evidence, and it is not translated. The reports gained `detail_code` so a script
never has to read a sentence; `status`, `failure_code` and `detail_code` read the
same in every language.

The **Details** list gained a filter - **All files**, **Only failures**, **Only
successes** - so a long batch can be read for just the files that need acting on;
"failures" is every file that was not renamed, the skipped ones included, which
is what the summary counts too. A count beside the filter reads `1 of 33 files`,
so a narrowed list cannot read as files that went missing. The choice survives a
language change and belongs to the batch on screen: the next batch opens showing
everything. Reading, naming and writing are otherwise unchanged, and the safety
rules are the same: originals are never modified, nothing is overwritten.

Also: a printed company name made only of characters Windows cannot store (`///`)
is now a reported failure keeping its PDF in `_unrenamed`, instead of a renamed
copy with an empty space in its name; a folder processed again no longer reads the
`DANFE_Renamed` folder back in, so the previous run's copies do not become this
run; the command line prints its counts, its reasons and its messages in the
chosen language, from the same table the window and the reports use, and says so
when a dry run writes nothing; and a Portuguese HTML report no longer repeats a
failure's reason in English after the Portuguese sentence. GPL-3.0-or-later.

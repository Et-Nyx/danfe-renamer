## DANFE Renamer 1.3.4

Os botões que escolhem os arquivos de entrada não falam mais só em PDF: a janela
lê **XML** por padrão desde a 1.3.0, e o botão continuava dizendo **Escolher
PDFs**.

### O que mudou
- **"Escolher Arquivos"** no lugar de **"Escolher PDFs"** — o mesmo vale para o
  título da janela de escolha dos arquivos.
- **O aviso de lista vazia mudou junto.** Ao clicar em **Processar arquivos** sem
  nada escolhido, a janela dizia "Escolha primeiro os PDFs ou a pasta que deseja
  processar"; agora diz **"Escolha primeiro os arquivos ou a pasta que deseja
  processar."**
- As regras de segurança continuam iguais: os originais nunca são modificados,
  nada é sobrescrito, e o que não dá para nomear continua virando uma linha com o
  motivo escrito.

### Uma nota que o SEFAZ não autorizou não é mais perdida
- **O XML de uma nota cancelada, denegada ou sem protocolo agora vira PDF e é
  renomeado como as outras.** Antes esses arquivos apareciam só como *ignorados*:
  o programa se recusava a gerar o DANFE e a nota não deixava nada no lote. Os
  dados (número, data, valor, emitente, destinatário) estão no XML
  independentemente do que o SEFAZ respondeu, então o nome é montado a partir
  deles.
- **O nome sai dos dados do XML, não do PDF gerado.** O XML é a fonte que o
  programa sempre usa; ler o PDF recém-gerado para tirar o nome daria o valor
  errado — `0,00` no lugar de `1.234,56`.
- **O motivo continua à vista.** A situação da autorização vira uma observação na
  linha do arquivo: a coluna **Motivo** na tela Detalhes, a coluna **Motivo** do
  relatório e a linha do `--verbose` dizem, por exemplo, `Situação da
  autorização 101: Cancelamento de NF-e homologado`, com as palavras do próprio
  protocolo. Uma nota cancelada que não dissesse nada seria uma armadilha para
  quem arquiva.
- **O que continua recusando um arquivo é o que deixaria o *nome* errado:** um XML
  ilegível, um documento que não é NF-e/NFC-e, uma chave que não confere com os
  dados. Nesses casos o PDF continua sendo guardado em `_unrenamed` quando há um
  modelo com que gerá-lo, para renomear à mão.

### Como usar
1. Baixe `DANFE_Renamer_v1.3.4.exe` abaixo (seção **Assets**).
2. Dê dois cliques. Se o Windows mostrar **"O Windows protegeu o seu PC"**,
   clique em **Mais informações** e depois em **Executar assim mesmo** (é normal
   para programas sem assinatura digital).
3. Processe o lote normalmente.

### Detalhes técnicos
- Windows 10/11 (64 bits). Não precisa instalar Python nem nada.
- Sem rede, sem telemetria: nada é enviado para lugar nenhum.
- Por dentro: a versão do programa é declarada em três arquivos
  (`app/__init__.py`, `pyproject.toml` e `packaging/version_info.txt`, que é o que
  o Windows mostra nas propriedades do `.exe`) e a suíte agora recusa uma versão
  que não seja a mesma nos três — foi assim que a 1.3.3 saiu com o
  `version_info.txt` ainda dizendo 1.3.2. As notas de cada versão também passaram
  a ser cobradas pela suíte.

### English summary
The buttons that choose the input files no longer say "Choose PDFs": the window
has read XML by default since 1.3.0, and the button kept naming only one of the
two kinds a batch accepts. It now says **Choose Files**, and so does the title of
the file chooser it opens; the alert shown when **Process Files** is pressed with
nothing selected said "Choose the PDF files or the folder you want to process
first" and now says **files**. The safety rules are the same: originals are never
modified, nothing is overwritten, and anything that cannot be named is still
reported with its reason written down.

**A note SEFAZ did not authorize is no longer lost.** A cancelled or denied note -
or one with no protocol at all - used to be reported as skipped with nothing
produced: no DANFE, no file to hand in. Its fields are on the XML whatever the
status is, so it is now read, converted and renamed like any other, and the status
travels as a note on the row: the details list's Reason column, the report's
Reason column and `--verbose` say `Authorization status 101: ...`, with the
protocol's own words kept as evidence. The name comes from the XML's own data and
not from the rendered PDF, which would get the total wrong (`0,00` for
`1.234,56`). What still refuses a file is what would make the *name* wrong - an
unreadable XML, a document that is not an NF-e/NFC-e, a key that disagrees with
the data - and those keep their PDF in `_unrenamed` when there is a model to
render.
